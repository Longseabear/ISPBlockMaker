# Crop analysis and managed inputs

Use this reference for numerical RAW inspection, WB estimation or turning the user's crops into reusable inputs. Read [common.md](common.md) for discovered paths and [viewer.md](viewer.md) for image import, crop geometry and delivery semantics.

## Read the intended delivery

`isp viewer-crops` returns the latest explicitly sent selection: `id`, `status`, `purpose` (`analysis`, `white_balance`, `input`), shared `description`, resolved `crops[]`, and `missing`. Per-item descriptions supplement the shared instruction. Purpose is a UI hint, not a restriction: the actual user request can combine analysis, WB and reusable inputs. Keep the delivery ID and each request/crop ID with results. Read-only inspection does not acknowledge or start work. A consumed delivery is previous work; reanalyse only when the user asks. For a new task request a region with `viewer-request IMAGE_ID --purpose white_balance --message "Select neutral, unclipped patches"` (or `--purpose input`).

Re-read before processing. Do not substitute another saved region for a missing/deleted one. For grouped items, process every `regions[].paths.crop`; top-level `paths.crop` is a ZIP and top-level ROI/preview only represents the first region. The source copy hash and output spec identify actual pixels. If the latest delivery changed while working, retain your original IDs; never acknowledge a newer delivery merely to clear its pending state.

After fulfilling the request and recording useful results, call `isp viewer-crops-ack DELIVERY_ID --note "ROI IDs; calculation/result or input paths; limitations"`. This updates the user's delivery receipt. Do not acknowledge a successful result before it exists. If blocked, explain the missing information and leave it pending. A stale-ID conflict requires checking the latest delivery, not retrying with its ID: report that the old delivery's results are saved but its receipt could not update, while the newer delivery stays pending. This acknowledgement is independent of JOB completion.

## Compact inspection, bounded context

Start with `isp viewer-crop-stats DELIVERY_ID [--black N] [--white N]`. It returns per-region/per-channel summaries, valid counts and a combined WB estimate, without image bytes or full pixel arrays. Source-region inspection is `isp viewer-stats IMAGE_ID --roi x,y,width,height [--black N] [--white N]`. Large requests exceeding the service sample budget need local streaming/tiled processing; do not silently downsample numerical calculations.

For individual values, use `isp viewer-pixels IMAGE_ID --roi x,y,width,height`. The CLI requires an explicit ROI of at most 256 source pixels. RAW values are original valid-bit samples, not gamma-corrected display values. API/UI pixel windows have their own bounded limit. CFA channel labels reflect the source pattern, grouping and origin; Gr and Gb are distinct green positions. The UI's default pixel labels appear only when pixels are large enough to read.

Never `cat`, decode-as-text, print base64, or emit `.tolist()` for a full RAW/image into the conversation. Open binary files with a local decoder or array/memory-map tool and output only requested measurements, small samples and file paths. Keep scripts/intermediate images in `<tmpDir>/<task-id>/`. If native image input is available, open a crop preview or the current-view PNG using that tool; do not paste image data into a text response. `viewer-image --vision` returns a PNG path for this purpose. Integrations can request `attachment?vision=true` only when they forward returned image blocks natively; oversized attachments fall back to paths. Preview PNGs are display evidence, never a source for RAW statistics.

## White balance

- Establish the actual black level, white/saturation level, pattern/group/phase and whether the selection is neutral. The generic defaults are not measured sensor calibration. When unknown, report channel statistics and any gains as provisional assumptions, rather than claim calibrated WB. Display levels are not necessarily sensor black levels.
- Inspect per-region R/Gr/Gb/B counts, means, valid means, clipping counts and variation. The service excludes values at/below black and at/above white from valid means. Avoid unstable estimates with zero/too few valid samples, clipping, dark patches or strongly varying illumination. A flat patch is not necessarily gray; a deliberately red object cannot calibrate WB.
- Use valid, black-subtracted means to estimate G/R and G/B, with green normalized to 1. Combine Gr/Gb with sample-count weighting; retain their individual means to reveal imbalance. The aggregate pools selected regions by valid sample count; overlapping regions are counted independently, and mixed lighting can make the pooled result misleading. Compare region estimates before choosing a global gain.
- Preserve the RAW source. If requested, implement/apply gains to a new result, verify clipping and explain assumptions. A report/chart goes to [Visualizations](../isp-visualizations/SKILL.md); display-only inspection uses Image Viewer. Do not change the graph or color pipeline merely because the user asked for a calculation.

## Reusable input data

When the user requests reusable inputs, including alongside WB regardless of the selected purpose, use the description to establish the intended input; the purpose itself does not authorize unrelated graph changes. Use exact crop files, not rendered screenshots. Record request/crop/region IDs, source hash and ROI, output dimensions, bit depth/alignment, Bayer pattern/group/origin, and resulting hash/path. RAW crops use 16-bit little-endian containers with tightly packed rows and zero output CFA phase; trust the returned spec rather than reusing source padding/offset.

Viewer crop files are framework-managed and can be deleted by the user. If asked to make stable reusable inputs, copy the requested region files and a compact manifest into a dedicated `<dataDir>/<input-name>/` folder, checking existing destinations before replacement. Keep this folder outside `sourceRoot` by default; reference it from the graph only when that change is part of the request. Preserve originals and make one manifest entry per region rather than flattening unrelated regions into a bounding-box crop. Register/attach the resulting input paths to the requested JOB or analysis summary, then acknowledge the delivery with those paths. Input bundles require the relevant input files to be explicitly included; do not claim they travel with code-only exports.
