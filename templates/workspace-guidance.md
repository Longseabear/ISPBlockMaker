## ISP work checkpoints

These instructions apply to this workspace and its subdirectories. Follow the user's task and constraints; this guidance does not authorize unrelated changes or external sharing.

- **Establish context.** At task start, discover `workspace-info`, read `graph-info`, affected block contexts and relevant project skills, and check actual source. Keep the task's block targets stable; clicking another node does not silently change the assignment. Inspect existing edits before modifying them.
- **Reconcile the affected graph.** At meaningful implementation/validation milestones and completion, use `.agents/skills/isp-block-maker/change-impact.md` to select affected records and checks. `graph-check` provides read-only structural/reference findings and shared-file impact, not proof of prose contracts or algorithm correctness. Update verified in-scope differences only; unchanged metadata needs no write.
- **Put knowledge where it belongs.** Keep card descriptions short; put human explanations in Detail, precise I/O/numerics/state in agent contracts, and project purpose/run commands/cross-block constraints in the overview. Use freeform notes where useful. Preserve stable IDs and useful user notes. Per-run results belong in activity/attempt/artifact records rather than timeless graph claims.
- **Verify the changed guarantee.** Use `.agents/skills/isp-block-maker/validation-method.md` to select relevant invariants, cases and acceptance criteria. Use existing commands or reusable execution recipes when appropriate, retaining their actual run conditions/source identity. Recipe manifests and successful execution do not prove algorithm correctness. No exhaustive ISP checklist or experiment is required for trivial edits.
- **Keep user work coherent.** Use the revision actually read for mutations. Re-read and reconcile conflicts instead of blindly retrying. Respect cancelled/deleted JOBs and user edits. A read-only question, crop/view adjustment or queue registration does not require code changes. Operate through the workspace CLI rather than rewriting framework-managed local records.
- **Learn reusable methods.** After verifying a repeatable execution, analysis or adaptation procedure, assess whether to improve an existing project skill or create one. Record trigger, prerequisites, parameterized steps, input/output and success checks. Do not turn every thought, failed guess or run log into a skill. Read only relevant skills.
- **Finish visibly.** For substantive changes, record a concise work summary and show affected graph blocks/edges or the useful registered result, respecting the user's chosen view and unsaved edits. Reports/plots belong in Visualizations; `report-build` can create a self-contained HTML file from measured data, and registration/presentation remain explicit. Source image inspection belongs in Image Viewer; explicit SDD requests belong in Documentation. Follow `.agents/skills/isp-block-maker/completion.md`.
